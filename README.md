# Student Organization Management System

## Доступ стажёров без регистрации

Стажёры входят по общему коду и получают отдельный JWT на 30 дней, без создания
пользователя. Смена кода отзывает все прежние сессии при следующем запросе.
Код сохраняется в SQLite, генерация атомарна между worker-процессами.

- `GET /api/trainee-code` — текущий код (до первой генерации `null`).
- `POST /api/trainee-code` — сгенерировать новый код и отозвать предыдущие сессии.
- Оба маршрута требуют обычный JWT; разрешены только admin/админ, председателю,
  председателю студсовета и заместителям председателя. Флаги остальных должностей
  не дают права управлять кодом.
- `POST /api/trainee/login` с JSON `{ "code": "..." }` — гостевой JWT.
- `GET /api/trainee/session` — проверка срока и версии кода.
- `GET /api/trainee/categories`, `/api/trainee/cards`, `/api/trainee/cards/{id}` —
  чтение с гостевым JWT. Только карточки с `trainee_access=true` и содержащие их
  категории. Пользовательские списки доступа не выдаются.

`trainee_access` настраивается в обычных POST/PUT карточек и по умолчанию `false`.
Обновление существующих SQLite-баз через `ensure_schema_upgrades()` сохраняет
данные и закрывает старые карточки для стажёров. `create_all()` создаёт новую
таблицу `trainee_code`. Файл рабочей БД не нужно заменять при деплое.

Тесты: `python -m unittest discover -s tests -v`. Они используют отдельную
временную SQLite-базу, не рабочий `app.db`; дополнительных test-зависимостей нет.
Для браузерной проверки: запустить `python tests/serve_trainee_smoke.py`, затем
следовать инструкции в README фронтенда. Сервер использует временную базу
на `127.0.0.1:8000`; не запускайте его вместо работающего сервера с данными.

Система управления студенческой организацией с JWT аутентификацией, ролями и должностями.

## Модель данных

### Должность (Position)

- **id**, **name** (уникальное название)
- **hierarchy_level** - уровень иерархии (1 = высший, 10 = низший)
- **can_register_users** - регистрация пользователей
- **can_edit_categories** - редактирование категорий
- **can_delete_categories** - удаление категорий
- **can_edit_cards** - редактирование карточек
- **can_delete_cards** - удаление карточек
- **can_edit_any_user** - редактирование любых пользователей
- **can_manage_positions** - управление должностями (создание/редактирование/удаление)
- **created_at**

### Пользователь (User)

- login, password_hash
- first_name, last_name, middle_name
- birth_date
- course, group
- **position_id** (ссылка на Position)
- department
- telegram
- is_active, is_deactivated
- last_login

### Категория (Category)

- name, description
- created_at

### Карточка (Card)

- title, content (markdown)
- category_id
- access_positions, access_logins (для ограничения доступа)
- created_at

## База данных

SQLite база данных хранится в файле `app.db` и **не пересоздается** при каждом запуске.
Данные сохраняются между перезапусками приложения.

Для пересоздания БД с начальными данными:

```bash
rm app.db && python3 seed_db_v2.py
```

## Безопасность

- JWT токены живут 30 дней
- Пароли хешируются с помощью bcrypt
- Все endpoints кроме `/api/login` требуют JWT токен в заголовке `Authorization: Bearer <token>`
- Ролевой доступ реализован через таблицу должностей (Position)
- Управление должностями доступно только пользователям с `can_manage_positions=True`
- **Пользователи не могут редактировать себя** - для изменения своих данных обратитесь к администратору

## Оборудка

`equipment.py` — учёт аппаратуры с историей. Новые таблицы `equipment_items`,
`equipment_locations`, `equipment_history` создаются через существующий `create_all`.
Исходные таблицы и данные не перезаписываются; отдельный reset/seed не нужен.
«в главке» создаётся идемпотентно при первом запросе вариантов держателя или добавлении предмета.

Все активные пользователи могут смотреть таблицу и историю, а также брать предметы
на себя. Только admin/админ, председатель и его замы, председатель студсовета,
руководители отделов и их замы могут добавлять предметы, места и вручную править записи.
Право `can_edit_any_user` само по себе не даёт доступа к ручному редактированию.
Accountless trainee-сессии не имеют доступа к оборудованию.

- `GET /api/equipment` — таблица.
- `GET /api/equipment/options` — `can_manage`, активные пользователи, места и место по умолчанию.
- `POST /api/equipment/locations` — новое общее место хранения, имя уникально без учёта регистра.
- `POST /api/equipment` — предмет: `name`, `description`, `holder_user_id` или `location_id`, необязательный `taken_at`.
- `PATCH /api/equipment/{id}` — ручная правка; обязательна текущая `version`.
- `POST /api/equipment/{id}/take` — только `{ "version": N }`, держатель и время определяются сервером.
- `GET /api/equipment/{id}/history` — неизменяемые записи, новые сверху; видны всем участникам.

При устаревшей версии возвращается 409. Состояние и история сохраняются атомарно.
История хранит снимки имени/логина держателя и автора записи, дату взятия и время записи.
Передача в место хранения очищает текущую дату взятия; прошлые взятия остаются в истории.
Исправление даты также фиксируется в истории. Правка только описания/названия не создаёт взятие.
Время хранится в UTC, фронтенд отображает локальное время пользователя.

Проверка: `python -m unittest discover -s tests -v` — изолированная временная БД.
Браузерная проверка: `python tests/serve_equipment_smoke.py` (127.0.0.1:8012),
затем см. README фронтенда. Пользователи фикстуры admin/member с паролем smoke-password
существуют только во временной БД; этот сервер не предназначен для продакшена.


## Поля аккаунта и предупреждения

`phone` — необязательная строка (7–15 цифр; допускаются +, пробелы, скобки, дефисы;
до 40 символов с форматированием). `education_format` — `бюджет` / `платное` или null.
Поля доступны в обычной и пакетной регистрации, редактировании и ответах пользователей.
Переданный null очищает эти два поля; отсутствие поля сохраняет старое значение.
Для старых БД `ensure_schema_upgrades()` добавляет nullable-колонки до запросов seed/ORM.

`member_warnings.py` хранит предупреждения в новой таблице `member_warnings`.
Счётчики и причины отсутствуют в общих ответах аккаунтов и выдаются отдельными API:

- `GET /api/warnings/permissions` — флаги `can_view` / `can_manage` текущего участника.
- `GET /api/warnings/counts` — количества действующих предупреждений по user ID.
- `GET /api/users/{user_id}/warnings` — вся история, новые записи сверху.
- `POST /api/users/{user_id}/warnings` — `{ "reason": "Обязательная причина" }`.
- `POST /api/warnings/{warning_id}/remove` — `{ "reason": "Обязательная причина снятия" }`.

Выдают/снимают только admin/админ, председатель и его заместители. Председатель
студсовета, руководители отделов и их заместители дополнительно могут смотреть
количество и историю, но не изменять предупреждения. Секретарь, участники и стажёры
не имеют доступа к предупреждениям, включая собственные. Несвязанные флаги редактирования
аккаунтов не расширяют эти права. Ответы предупреждений имеют Cache-Control: no-store.

Несколько действующих предупреждений разрешены. Снятие не удаляет запись: сохраняются
исходная причина, имя/логин выдавшего, дата выдачи, причина снятия, имя/логин снявшего
и дата снятия. Повторное/одновременное снятие возвращает 409, исходный аудит не меняется.

`DELETE /api/equipment/{id}` с `{ "version": N }` — удаление из списка только
admin/председателем/его заместителями. Это архивирование через `deleted_at`:
предмет исчезает из списка и профиля держателя, но записи и история перемещений
сохраняются; API истории по ID остаётся доступен участникам. Устаревшая версия — 409.
Колонка `deleted_at` добавляется существующим БД идемпотентно; данные не сбрасываются.

Проверки: 40 backend-тестов, новая миграция, отрицательные права, обязательные причины,
одновременное снятие, архивирование/конфликты версии; всё на временной БД.
